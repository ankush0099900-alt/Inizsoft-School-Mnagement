INIZERP — SaaS Architecture Evaluation Report

Technical Decision Document for Project Management & Leadership

Scope: 5 to 500+ Schools Stack: Next.js + Express + PostgreSQL (Prisma)
Executive Summary: This technical evaluation compares the two fundamental multi-tenant database paradigms for InizERP: Option A: Separate Database per School (Database-per-Tenant) vs. Option B: Shared Database with Tenant Isolation (Single Database Multi-Tenancy). It directly addresses the leadership's primary concerns: system reliability (ensuring one school's issue does not crash others), custom branding/domains per school, independent online fee collection, and scalability to hundreds of schools.

1. Architectural Models Overview

Option A: Separate Database per School Isolated Tenant

Concept: Every registered school gets its own completely isolated PostgreSQL database (e.g. db_school_dps, db_school_dav). A central Master DB stores credentials and routes incoming requests.

[Request: dps.inizerp.com] │ [Backend Router] │ ┌───────┴───────┐ ▼ ▼ [Master DB] [DB: DPS Delhi] (Isolated Tables)

Used by: High-security Gov/Banking portals requiring physical tenant air-gapping.

Option B: Shared Database with RLS Industry Standard SaaS

Concept: A single, high-performance PostgreSQL database serves all schools. Every single table contains a mandatory indexed schoolId column enforced by Middleware and Row-Level Security.

[Request: dps.inizerp.com] │ [Backend Router] │ ┌───────┴─────────────────┐ ▼ ▼ [Central PostgreSQL Database] └─ Students (WHERE schoolId = 'dps-uuid') └─ Invoices (WHERE schoolId = 'dps-uuid')

Used by: Shopify, Salesforce, Slack, Workday, GitHub.

2. In-Depth Pros & Cons Analysis

Option A: Separate Database

✅ Advantages (Fayde):

  • Zero Blast Radius for Data Corruption: If School A's database faces corruption or table lockup, School B & C are physically unaffected.
  • Independent Backup & Rollback: If a school accidentally deletes their exam records, only that school's database is restored without taking other schools offline.
  • Zero Data Leakage via Code Bug: Since DBs are separate, an accidental developer omission of WHERE schoolId = ... cannot leak cross-school data.
  • Easy Tenant Offboarding: If a client leaves, you can hand over their standalone .sql dump file cleanly.

❌ Critical Disadvantages (Nuksan):

  • Disastrous Migration Bottlenecks: Adding a column requires running migrations across all 200–500 databases in a loop. If database #142 fails mid-migration, the system enters an unrecoverable version mismatch state.
  • Severe Connection Exhaustion: Prisma opens connection pools per database. 100 schools × 10 connections = 1,000 open connections. Server crashes due to Out-Of-Memory (OOM).
  • Exorbitant Infrastructure Cost: 100+ separate managed database instances require heavy cloud expenditure ($$$$).
  • Super Admin Analytics Impossible: Generating platform-wide revenue or user counts requires querying 500 individual DBs sequentially, causing severe latency.

Option B: Shared Database (Recommended)

✅ Advantages (Fayde):

  • Seamless 2-Second Migrations: Schema changes are deployed in one single atomic command (prisma migrate deploy) for all 500+ schools instantly.
  • Optimal Connection Pooling & RAM: Uses a single connection pool with PgBouncer. A single 4GB RAM server easily handles 100,000+ students and teachers across hundreds of schools.
  • Extremely Low Infrastructure Cost: Requires only 1 managed PostgreSQL cluster with automated backups, saving thousands of dollars per year.
  • Real-Time Super Admin Analytics: Instant aggregated dashboards (MRR, total active students, global attendance trends) via standard SQL joins.
  • Aligns 100% with Existing Codebase: InizERP's 50+ Prisma models are already structured with schoolId foreign keys.

❌ Potential Risks & Their Mitigations:

  • Risk: Single Point of Failure?
    Mitigation: Handled by High-Availability (HA) Master-Replica. If the primary node crashes, the secondary node automatically takes over within 15 seconds.
  • Risk: Data Loss / Accidental Deletes?
    Mitigation: Handled by Point-in-Time Recovery (PITR) and Soft Deletes (isDeleted: true). Any deleted record can be restored with a single toggle.
  • Risk: Heavy User Slows Down Others (Noisy Neighbor)?
    Mitigation: Handled by Express tenant rate-limiting and read-replicas for intensive reporting.

4. Addressing the Two Biggest Stakeholder Myths

Myth 1: "Do we need separate databases so schools can have their own Custom Domain?"

Fact: NO. Custom Domains are 100% independent of the database architecture.

Whether using a shared database or separate databases, domain routing works via the HTTP Host header in the Next.js and Express middleware. When a user visits portal.dpsdelhi.com or dps.inizerp.com, the middleware looks up the domain in a cached table, binds the corresponding schoolId, and serves that school's custom logo, colors, and data.

Myth 2: "Can each school collect student fees directly into their own bank account?"

Fact: YES. Each school receives 100% of student fee payments into their own bank account.

InizERP includes a SchoolPaymentConfig model. Each school inputs their own Razorpay or Stripe API keys and Secret. When a parent pays fees online, the payment order is created directly under that school's gateway account. Funds settle directly into the school's bank account with zero SaaS platform intermediary liability or GST complications.

Final Engineering Recommendation for Project Management

Adopt Option B: Shared Database with High-Availability & Robust Backups (or the Hybrid Tiering Model).

Building a separate database per school for a commercial SaaS targeted at hundreds of schools will result in severe technical debt, memory exhaustion in Node.js/Prisma, and fragile schema migrations. The current InizERP codebase is already 95% architected for Shared Database isolation. Leadership's concerns regarding reliability and privacy are fully addressed through High-Availability clustering, Point-In-Time Backups, Soft Deletes, and Row-Level Security — giving you the maximum reliability with the lowest operational cost.
